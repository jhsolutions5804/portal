# 7.29 — 근태 출역 인원수 카운트 버그 수정 (v5.3.5 / daily-report 2.4.2)

**날짜**: 2026-08-22
**대상**: `pjt/index.html`(FAB), `daily-report/index.html`(FAB)

## 배경
대표가 근태 탭에서 8/21 날짜를 보다가 "기술인 출역 현황 출역 9명 / 전체 5명"이라는 이상한 숫자를 발견. 명단에는 5명(서민우 팀장·심산·이미정·이승준·태상원)만 체크박스로 보이는데 배지엔 9명이라고 표시됨. 공사일보의 "기술인 투입 현황"도 "전체 9명 중 출역 9명"으로 실제 인원과 다르게 표시됨.

## 조사

### 1차 진단 (부분적으로 틀림)
처음엔 "근태 탭 화면이 명단에서 삭제된 인원을 숨기고 있어서 그렇다"고만 진단하고, 삭제된 인원도 "◯◯◯ (삭제됨)" 형태로 화면에 같이 표시하는 패치를 적용 → portal-test 배포. 그런데 실제로 확인해보니 이 4명은 마스터 명부(`master_workers`)에 연결되지 않은 채(마스터에서 선택이 아니라 직접입력으로) 근태 탭에 추가됐던 인원이라, 삭제된 뒤엔 이름을 복구할 방법이 전혀 없어서 전부 "알 수 없음"으로만 표시됨. 대표가 이 화면을 보고 "안보이게 하는 게 맞다"고 판단 → 삭제된 인원 표시 기능 자체를 되돌림 (portal-test에서 revert 커밋).

### 2차 진단 (실제 원인)
대표가 재차 질문: "전체 인원이 5명인데 왜 9명이 출역으로 잡히냐". 다시 코드를 보니 진짜 문제는 표시 여부가 아니라 **카운트 로직 자체**였음.
- `worker_attendance/{날짜}.checks` 배열은 그 날짜 당시 실제 체크된 인원 ID 그대로 보존됨 (명단 삭제 시 확인창에 "기존 공수·출역 데이터는 유지됩니다"라고 명시된 의도된 설계)
- 그런데 "출역 N명" 배지(`pjt/index.html`)와 "투입 현황"(`daily-report/index.html`)이 이 `checks.length`를 **필터링 없이 그대로** 써서, 명단에서 이미 삭제된 인원의 과거 체크까지 숫자에 포함되고 있었음
- 추가로 `daily-report/index.html`은 "전체 인원" 자체를 `data.js`에 **하드코딩된 정적 `WORKERS` 배열(9명 고정)**로 계산하고 있어서, 근태 탭에서 명단을 아무리 바꿔도 절대 갱신되지 않는 별개의 버그도 겹쳐 있었음

## 구현
1. `pjt/index.html`
   - "출역 N명" 배지: `checks.filter(id => _ws.some(w=>w.id===id))`로 현재 명단에 실재하는 ID만 카운트
   - 홈 화면 "오늘 출역" KPI: 동일하게 `getWorkers()` 기준 필터링 적용
   - (되돌림) 삭제된 인원을 "(삭제됨)"으로 화면에 표시하는 기능은 이름 복구 불가 문제로 제거
2. `daily-report/index.html`
   - 하드코딩 `WORKERS` 배열 참조 완전 제거
   - `pjt_workers_fab` + `master_workers`(퇴사일)를 `Promise.all`로 실시간 조회해서 "전체 인원" 계산 (근태 탭과 동일 필터 로직: 조회 날짜 기준 퇴사자 제외)
   - "출역 인원"도 위와 동일하게 유효 명단 ID로 필터링

## 검증
- `<script type="module">` 블록 추출 → `node --check` 문법 검증 통과
- HTML `<div>` open/close 태그 개수 일치 확인
- portal-test 배포 → 대표 실 확인: 8/21 기준 "출역 5명 / 전체 5명"으로 정상 표시 확인 (`ㅇㅋ 된다`)
- 프로덕션 배포 후 파일 내용 재조회하여 배포본이 로컬 패치본과 완전히 일치함을 확인

## 교훈
- 첫 진단에서 "화면에 안 보이는 게 문제"라고 성급히 결론 내리고 바로 UI 추가 기능을 만들었다가, 대표의 재질문으로 실제 원인(카운트 로직 자체의 버그)을 다시 찾아야 했음. 진단 단계에서 "왜 이 숫자가 나오는지"의 계산식 자체를 먼저 끝까지 추적했어야 함
- `daily-report`가 하드코딩된 정적 데이터를 갖고 있다는 사실이 이번에도(2번째) 문제의 원인이 됨 — 8/21 세션의 Auth 초기화 누락 건과 마찬가지로, standalone 모듈이 메인 포털과 별도로 관리되면서 생기는 반복 패턴. `daily-report`의 나머지 하드코딩 데이터(`ALL_SCHEDULE` 등)도 향후 유사 문제가 없는지 점검 필요
