- 2차(2026-07-27, v1.0.2): **`pjt_manday/index.html` 자체에 로그인+관리자 검증을 추가**해 우회 경로를 닫음.
  - 페이지 로드 시 Firebase Auth 로그인 여부 확인 → 로그인된 사용자의 `portal_users/{uid}` 문서에서 `admin===true && status==='approved'`를 실제로 조회해서 확인한 뒤에만 데이터 조회(`loadMonth()`) 시작
  - 검증 실패 시 "🔒 접근할 수 없습니다" 화면만 표시, Firestore 조회 자체가 실행되지 않음
  - 기존에 `?admin=1` URL 파라미터로 판단하던 일당(급여) 표시 여부도 이 검증 결과로 전환 — URL 조작만으로 급여 노출되던 문제 해결
  - 같은 Firebase 프로젝트·도메인을 쓰는 포털 메인 로그인 세션이 그대로 인식되므로, 정상적으로 포털에 로그인한 관리자는 재로그인 불필요


## 개요

FAB·SUP·경량 PJT 전체에 걸쳐 발생하는 공수를 한 화면에서 PJT별·개인별·팀별로 집계한다. 근로자 식별은 **이름+생년월일**을 고유 키로 쓰는 **마스터 명부**를 통해 이루어지며, 같은 사람이 여러 PJT를 겸직해도 자동으로 한 사람으로 합산된다.

---

## 데이터 소스 (⚠️ 컬렉션이 프로젝트마다 다름)

| PJT | 근로자 명단 | 출역 | 공수 |
|-----|------------|------|------|
| FAB | `pjt_workers_fab` | `worker_attendance` | `worker_manday` |
| SUP | `pjt_workers_ph4` | `ph4_attendance` | `ph4_manday` |
| 경량 PJT | `pjt_registry/{id}/workers` | `pjt_registry/{id}/attendance` | `pjt_registry/{id}/manday` |

> FAB와 SUP는 컬렉션을 **공유하지 않는다**. "같은 컬렉션을 공유한다"고 잘못 가정했던 초기 설계 버그로 한동안 SUP 공수가 집계에서 누락됐던 이력 있음(2026-07-24 수정).

## 근로자 마스터 명부 (`master_workers`)

- 문서 ID: 마이그레이션 시 그 사람이 처음 발견된 프로젝트의 로컬 워커ID를 그대로 재사용 (신규 등록 시엔 `이름_생년월일` 형태로 생성)
- 필드: `name`, `birth`(YYYY-MM-DD, 고유 식별 코드 역할), `leaderId`(소속 팀장의 마스터ID, 비어있으면 팀장/독립), `dailyRate`(일당, **관리자에게만 표시**)
- 팀 구조는 **1단계만** (팀장의 팀장 없음)
- CRUD: "근로자 마스터 관리" 카드에서 등록(`openMasterForm`)/수정(`editMaster`)/삭제(`deleteMaster`, 팀장으로 지정된 사람은 팀원 정리 전까지 삭제 불가)

### 이름·생년월일 자동 동기화 (v1.0.1, 2026-07-27)

- 각 프로젝트 근로자 명단(`pjt_workers_fab`/`pjt_workers_ph4`/`pjt_registry/{id}/workers`)에도 자체 `name`/`birth` 필드가 남아있으며, 마스터 명부 수정 시 이 문서들은 자동으로 갱신되지 않는다.
- 이 격차를 해소하기 위해 `pjt_manday`는 로딩 시 `master_workers`를 먼저 조회하고, **근로자 ID가 마스터 ID와 일치하면 이름·생년월일을 마스터 값으로 항상 덮어써서 표시**한다(`loadRoster()`의 `masterMap` 오버레이).
- 따라서 "근로자 마스터 관리"에서 생년월일을 등록/수정하면 개인별 합계·팀별 합계 등 이 화면 전체에 즉시 반영된다.
- 상단 "생년월일 미입력" 경고는 이제 **마스터 명부에도 등록되지 않은 진짜 미등록자**만 표시된다.
- ⚠️ 단, 각 프로젝트 로컬 문서의 `name`/`birth` 필드 자체는 그대로 남아있다(화면 표시만 오버레이). 완전한 정합성을 위해서는 "기존 인원 마이그레이션" 도구로 로컬ID를 마스터ID로 통합하는 것을 권장한다.

### 기존 인원 마이그레이션

- "🔄 기존 인원 마이그레이션" 버튼 → FAB/SUP/경량 PJT의 현재 로스터를 이름 기준으로 그룹핑해서 표시
- 그룹별로 생년월일(필수)·소속 팀장·일당 입력 후 "마스터로 등록" → `confirmMigrate()`
  - 마스터 ID = 그룹 내 **첫 번째 항목의 로컬 ID**를 재사용 (그 프로젝트의 과거 출역/공수 이력이 끊기지 않음)
  - 나머지 프로젝트: 마스터ID로 새 워커 문서 생성 + 기존 로컬ID 문서 삭제 → 이후 그 프로젝트에서 발생하는 공수는 마스터ID로 저장되어 자동 합산
  - **주의**: 마이그레이션 직후 해당 프로젝트 탭이 이미 열려있으면 예전 명단이 메모리에 남아있으므로 반드시 새로고침 필요 (완료 알림에 안내 포함)
- 이미 등록된 사람은 목록에 "✓ 마스터 등록됨" 표시 + "✏️ 등록정보 수정" 버튼으로 바로 수정 가능

### 각 PJT의 "인원 추가" 방식 변경

- FAB/SUP/경량 PJT 전부 "이름 직접 입력" → **마스터 명부에서 선택하는 드롭다운**으로 전환
- 선택 시 그 프로젝트의 워커 문서를 **마스터ID를 그대로 문서ID로 사용**해서 생성 (`_fbAddWorkerFromMaster` / 경량 PJT는 `saveWorker`) → 이후 사후 이름+생년월일 매칭 없이도 ID 자체가 통일됨
- 마스터 명부에 없는 신규 인원은 먼저 월간 공수 탭에서 등록해야 함 (안내 문구 표시)

## 집계 로직

- 월 선택(`mShift`) → 해당 월의 날짜별 공수 문서를 FAB(`worker_manday`)/SUP(`ph4_manday`)/경량 PJT(`pjt_registry/{id}/manday`) 각각 순회
- 각 workerId를 해당 프로젝트 로스터와 대조해 소속 판별 → PJT별 합계(`pjtTotals`)에 가산
- 이름+생년월일(`personKeyOf`)로 개인별 합계(`personMap`)에 가산, 날짜별 세부내역(`byDate`)도 함께 기록
- **PJT별 합계는 공수 0인 프로젝트도 항상 표시**(로딩 실패와 데이터 없음을 구분하기 위함), 등록 인원수도 함께 표기
- 명단에 없는 workerId로 기록된 공수는 "소속불명" 경고로 카운트(`unknownIdCount`)

## 팀별 합계 (2026-07-27, v1.1.0에서 팀 단가 방식으로 변경)

- 마스터 명부의 팀장(=leaderId 없는 사람) 기준으로 그룹핑
- 각 팀은 팀장 본인 + 소속 팀원의 공수를 합산 표시
- **금액 계산 방식 변경**: 기존엔 팀원 각각의 개인 단가(`dailyRate`)×공수를 더해 팀 금액을 산출했으나, 대표님 요청("개인별로 얼마 나가는지는 중요한 정보 아니다")에 따라 **팀 단가(`teamRate`) × 팀 총공수**로 계산하도록 변경
- `teamRate`는 팀장의 `master_workers` 문서에 저장되는 필드로, 개인별 `dailyRate`와는 별개
- 관리자는 팀 헤더의 ✏️ 버튼으로 팀 단가를 바로 입력/수정 가능 (`editTeamRate()`)
- 팀별 합계 화면에서 팀원 개인별 금액은 더 이상 표시하지 않음(공수만 표시). 금액은 팀 단위로만 관리자에게 표시
- **개인별 합계(상단) 섹션은 영향 없음** — 그쪽은 여전히 개인별 `dailyRate` 기준으로 표시
