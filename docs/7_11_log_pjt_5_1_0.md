# 7.11. 개발로그 — PJT 5.1.0 (FAB/SUP 종료·재개 확장, 종료 PJT 전용 뷰)

> 작업일: 2026-07-26 · 작성: 춘식이(Claude)

---

## 배경

5.0.0 배포 후 대표님이 본섭에서 PJT 홈을 확인하던 중, "종료된 프로젝트" 섹션에 과거 테스트로 종료 처리된 화성 17L 카드가 남아있는 것을 발견 → 완전삭제 기능 우선 추가. 이어서 "진행 중인 프로젝트(FAB/SUP)가 실제로 완결되면 워크스페이스를 어떻게 정리하면 좋을지" 질문 → 데이터 보존 관점에서 삭제보다 종료(아카이브) 방식을 제안했고, FAB/SUP는 아직 종료 기능 자체가 없다는 점(하드코딩된 고정 메뉴라서)을 짚어 "미리 만들어두자"는 지시로 이어짐.

---

## 주요 변경

### 1. 종료된 프로젝트 완전삭제 (선행 작업)
- "종료된 프로젝트" 카드에 🗑 완전삭제 버튼 추가 (관리자 전용, 확인창 2회)
- `pjt_registry` 문서만 삭제되고, 하위에 쌓인 품목·근태·공수·일정·공사일보 데이터는 보존됨(고아 데이터로 남되 화면엔 노출 안 됨)

### 2. FAB/SUP 종료·재개 지원
- `PJT_FIXED_BASE` 상수 신설 — P4 Ph2/Ph4의 원본 정의(명칭·이모지·설명·URL)를 별도 보관. 배열에서 제거돼도 재개 시 이 원본으로 정확히 복원 가능
- 상태 저장은 `pjt_settings/{key}.status`(`active`\|`ended`) 필드 사용 — 워크스페이스 앱(`pjt/`, `pjt_ph4/`) 자체는 전혀 손대지 않음, 포털 사이드바/카드 노출 여부만 제어
- `syncPjtSubtabsFromSettings()`를 확장: 기존엔 이름/설명 동기화만 했으나, 이제 상태 확인 후 종료면 목록에서 제거·활성인데 없으면 원본에서 복원(항상 월간공수 앞에 삽입)
- 카드 ⚙️ 설정 모달의 "종료" 버튼을 경량PJT 전용에서 `pjt_home`/`pjt_manday`/`pjt_ended`를 제외한 전체 PJT로 확장

### 3. "종료 PJT" 사이드바 전용 메뉴 신설
- PJT 하위 메뉴 항상 최하단(월간공수보다도 아래)에 `🗄️ 종료 PJT` 고정 항목 추가
- 클릭 시 `showPjtEndedView()` — FAB/SUP(`pjt_settings` ended) + 경량 PJT(`pjt_registry` ended)를 하나의 화면에 모아서 카드로 표시
- `pjtRegistryCard()` 함수에 `kind`(`'fixed'`\|`'light'`) 파라미터 추가 — 고정 PJT는 재개만, 경량 PJT는 재개+완전삭제 노출
- 기존 PJT 홈 하단의 "종료된 프로젝트" 섹션(`renderPjtRegistry`)은 이 전용 뷰로 완전히 이전 — 중복 표시 제거

### 4. 실수 및 수정
- 함수 삽입 과정에서 `renderPjtHomeCards` 함수 시그니처 줄을 실수로 지워 문법 오류 발생 → `node --check`로 즉시 발견, 복구

## v5.1.1 (2026-07-27) — pjt_manday 개인별 생년월일 마스터 동기화

- FAB/SUP/경량PJT 로스터 로딩 3곳 모두 `masterMap` 전달하도록 수정
- 상단 경고 문구를 "마스터 명부에 미등록"이라는 의미가 드러나도록 보완

### 효과

- 이름 오타(태성원 vs 태상원)도 마스터 이름으로 통일 표시
- "생년월일 미입력" 경고는 마스터에도 없는 진짜 미등록자만 남음

## v5.1.3 (2026-07-27) — pjt_manday 페이지 자체 접근 검증 추가 (우회 경로 차단)

### 문제 인식
- 대표님 질문: "지금 본섭에 있는 세부 메뉴들이 독립된 url로 접근할 수 있게 설계 되어 있나?"
- 확인 결과: `pjt_manday/index.html`을 비롯한 모든 서브 메뉴가 GitHub Pages 같은 오리진 아래 독립 URL로 직접 접근 가능했고, `pjt_manday/index.html` 자체는 Firebase Auth를 아예 불러오지 않고 `?admin=1` URL 파라미터만으로 관리자 여부(급여 표시 포함)를 판단하고 있었음 — v5.1.2의 "관리자 전용 메뉴 숨김"은 포털 셸 UI에서만 걸려있어 URL 직접 접근은 막지 못하는 상태였음
- 대표님 지시: "우회 경로 없으면 좋겠는데" → "본섭에 바로 반영하고, 모든 하위 메뉴들에 똑같이 적용해줘"

### 수정 (`pjt_manday/index.html`, v1.0.1 → v1.0.2)
- `firebase-auth.js`에서 `getAuth`, `onAuthStateChanged` import 추가
- `isAdmin`을 더 이상 `?admin=1` URL 파라미터로 판단하지 않음 — 페이지 로드 시 로그인 사용자의 `portal_users/{uid}` 문서를 조회해 `admin===true && status==='approved'`를 확인한 뒤에만 `isAdmin=true`로 설정하고 `loadMonth()` 시작
- 검증 실패(미로그인 또는 비관리자) 시 "🔒 접근할 수 없습니다" 화면만 표시 — 이 경우 `loadMonth()`를 포함한 어떤 Firestore 조회도 실행되지 않음
- 부수 효과: 기존엔 URL 조작만으로 팀별 합계의 일당(급여) 정보까지 노출될 수 있었는데, 이번 수정으로 함께 차단됨

### 다른 하위 메뉴 전수 점검 결과 (모두 적용 지시받음, 진행 중)
- **edoc/index.html, gihoek/index.html**: 이미 자체 로그인+`portal_users` 승인 검증 로직 보유. 다만 `?via=portal`일 때 실제 승인/권한 확인을 건너뛰고 그냥 입장시키는 우회 버그 존재(주소창에 `?via=portal`만 붙이면 승인 안 된 계정도 진입 가능) — **패치 필요, 다음 커밋에서 진행**
- **pjt/index.html, pjt_ph4/index.html, pjt_light/index.html, hr/index.html**: Firebase Auth 자체를 아예 사용하지 않음 — pjt_manday와 동일한 구조적 문제. 단, 이 4개 파일은 pjt_manday와 달리 데이터 로딩 진입점이 하나로 모여있지 않고, 모듈 스크립트 곳곳에 즉시 실행되는 `onSnapshot` 구독과 `getDoc` preload가 여러 지점에 흩어져 있어(예: `pjt/index.html`의 `subscribeUserSchedules()`, `subscribeEdocLeave()`, `waitForFirebaseAndInit()` 폴링 체인 등) pjt_manday처럼 단일 지점에서 안전하게 막기 어려움. 전체를 안전하게 재구성하려면 파일별로 훨씬 큰 규모의 리팩토링과 회귀 테스트가 필요 — **대표님과 우선순위·방식 협의 후 진행 예정**

## v5.1.5 (2026-07-27) — FAB/SUP/경량PJT/HR 접근검증 게이트 추가 (portal-test 선검증)

### 배경
- v5.1.3에서 pjt_manday에 접근검증을 추가한 뒤, `pjt/index.html`·`pjt_ph4/index.html`·`pjt_light/index.html`·`hr/index.html`도 동일하게 자체 로그인 검증이 없다는 걸 확인 → 회귀 위험이 커서 대표님과 상의 후 **portal-test에서 먼저 검증하고 본섭 배포**하기로 결정

### hr — 가장 심각했던 케이스
- `?via=portal` 파라미터 존재 여부만으로 접근을 허용, Firebase Auth 자체가 없었음(구 설계 문서에도 "Firebase Auth 완전 제거"로 명시돼 있었음). 주소창에 `?via=portal`만 붙이면 급여·계약서 등 인사 데이터 전체 노출 가능
- `onAuthStateChanged` + `portal_users` 검증(`status==='approved' && (admin || perms.hr)`)으로 교체. `window._isAdmin`도 `?admin=1` 파라미터 대신 실제 검증 결과 사용

### pjt / pjt_ph4 — 구조가 복잡해 다중 지점 패치
- 두 파일 다 Firebase Auth 자체가 없었고, 데이터 로딩 진입점이 한 곳이 아니라 모듈 스크립트 곳곳에 흩어져 있었음(공수·공정 preload IIFE, `subscribeUserSchedules()`, `subscribeEdocLeave()`, `waitForFirebaseAndInit()` 폴링 체인)
- 로그인+`portal_users`(`perms.pjt`) 검증 게이트를 모듈 최상단에 추가하고, `window._accessGranted` 플래그로:
  - `waitForFirebaseAndInit()`의 폴링 조건에 편입 — 이 함수가 트리거하는 전체 UI 초기화 캐스케이드를 단일 지점에서 차단
  - 나머지 흩어진 자동실행 지점(preload 2곳, 구독 2곳, `applyOnLoad`/`renderProgress`)은 개별적으로 `window._accessGatePromise.then(ok=>{if(!ok) return; ...})`로 감쌈
- pjt_ph4는 pjt와 완전히 동일한 패턴, 컬렉션명만 ph4 접미사로 다름

### pjt_light — 단일 진입점이라 pjt_manday와 동일하게 깔끔히 처리
- `?admin=1` 파라미터로 판단하던 `isAdmin`을 실제 `portal_users.admin` 검증으로 전환, `init()` 호출을 검증 통과 후로 이동

### 검증
- 4개 파일 모두 `node --check` 문법 통과
- **portal-test에 firebaseConfig만 테섭용으로 교체해 동일 패치 배포** → 대표님이 직접 로그인 흐름(정상 접근)과 시크릿창 직접 URL 접근(차단 확인) 양쪽 다 테스트해서 확인("ㅇㅋㅇㅋ 전부 다 된다")
- 테섭의 pjt_manday도 본섭 v1.0.2와 동일 버전으로 맞춰서 함께 재배포(요청에 따라)

### 배포
- portal-test 검증 통과 확인 후 본섭 배포
- 커밋: `pjt/index.html`, `pjt_ph4/index.html`, `pjt_light/index.html`, `hr/index.html`
- 백업: `backup/v5.1.5/{pjt,pjt_ph4,pjt_light,hr}/index.html` (각 수정 전 원본)
