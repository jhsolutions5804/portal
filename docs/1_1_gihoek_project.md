**정산 내역 상태 표시**

- 완결(done): 초록 태그
- 폐기(void): 회색 태그

## 미수금 정의

```
미수금 = 청구액(pjtBilled) − 수금액(pjtDone)
       = 대금청구 누계 − 완결된 청구서 합계
```

- **완결(done) 처리된 대금청구서 = 수금 완료로 간주**
- 헬퍼: `pjtDone(pid)` — 완결 청구서 합계 (수금액)
- 헬퍼: `pjtDue(pid)` — 미수금 (`pjtBilled − pjtDone`)
- 표시 위치: 정산 탭 상단 요약 카드 / 기획 홈 KPI

---

## 집계 규칙

- **유효 견적 집계**: `status !== 'void' && status !== 'closed'`
- **청구 누계(pjtBilled)**: `status !== 'void'` (완결 포함, 폐기만 제외)
- **수금액(pjtDone)**: `status === 'done'` (완결 처리된 청구서)
- **미수금(pjtDue)**: `pjtBilled − pjtDone`
- **지급 집계**: `docType === 'payment' && status !== 'void'`

## PJT관리 자동 연동 (2026-08-29)

### 배경
기획(상업적 계약/견적 단위)과 PJT 관리(현장 운영/공정·공수 단위)가 별도 프로젝트 목록으로 관리되어 서로 어긋나는 문제가 있었음(예: 기획 "H17L" ↔ PJT관리 "화성 17L 개보수 현장"이 같은 프로젝트인데 이름이 달라 서로 인지 못함, PJT관리에만 있고 기획엔 없는 경량 PJT 존재).

### 연동 방향 결정
**기획 → PJT관리** 단방향. 이유: 계약/견적이 확정되는 시점(기획)이 현장 착수(PJT관리)보다 항상 선행하고, 견적서·정산서가 기획 소속 기능이라 프로젝트의 원본 정체성을 기획이 가져야 함. PJT관리가 독립적으로 프로젝트를 만들면 계약 없는 현장이 시스템에 등록될 위험이 있음.

### 스키마 추가
```js
gihoek_projects/{id}:
{
  ...(기존 필드),
  linkPjt:     'auto' | 'p4ph2' | 'p4ph4' | 'none' | 'reg_{pjt_registry문서id}',
  progProfile: string,   // 'p4ph2'|'p4ph4'|'' — 경량PJT(reg_*)는 빈 문자열(공정 자동연동 미지원, 향후 과제)
  mandayCol:   string,   // 'worker_manday'|'ph4_manday'|''
}
```

### 동작 방식 (`openPjtForm` / `savePjt`)
- "연동 PJT" 드롭다운: P4 Ph2/Ph4(고정 2개) + `pjt_registry`(경량 PJT, `status!=='ended'`)에서 실시간으로 불러온 전체 목록(`refreshLinkPjtOptions`) + "🆕 새 PJT관리 항목 자동 생성"(신규 등록 시 기본값) + "연동 없음".
- **신규 프로젝트 등록 시** `linkPjt==='auto'`(기본값)면, 저장 시 `pjt_registry`에 동일한 이름으로 경량 PJT 문서를 `addDoc`으로 자동 생성하고 그 문서 ID를 `reg_{id}` 형태로 `linkPjt`에 저장.
- **기존 PJT관리 항목과 연결**하려면 드롭다운에서 `reg_xxx` 옵션을 직접 선택(자동생성 아님, 중복 방지).

### 한계 / 향후 과제
- 경량 PJT(`reg_*`) 연동은 현재 "연결"만 되고, P4 Ph2/Ph4처럼 공정률·공수 데이터를 자동정산에 끌어오는 심화 연동(`progProfile`/`mandayCol` 기반)은 아직 구현 안 됨 — `type:'general'`(품목 직접입력)로만 운용됨.
- 기존 어긋난 데이터(H17L↔화성17L, M15X)는 스크립트가 아닌 화면에서 관리자가 직접 "연동 PJT" 드롭다운으로 재연결 필요(Firestore 직접 접근 불가로 인한 제약).

## 견적/정산 검색·페이지네이션, 프로젝트상세 레이아웃 개편, 뒤로가기 버그 수정 (2026-08-29b)

### 견적/정산 목록 검색 (드롭다운 방식)
주관식 텍스트 검색 대신, **작성된 문서에 실제로 쓰인 값만** 드롭다운 옵션으로 동적 추출(`estFilterOptions`/정산 동일 패턴).
- 견적: 현장명(연결PJT)·진행상태(연결PJT run/done)·거래처·발행월 4개 필터
- 정산: 구분·현장명·거래처·발행월·상태(완결/미결) 5개 필터. ⚠️ 정산에는 "진행상태"(연결PJT) 필터를 넣었다가 정산 고유의 "상태"(완결/미결)와 개념이 겹쳐 혼동을 준다는 피드백으로 **제거함** — 정산의 상태는 완결/미결 하나로 유지.
- 두 화면 모두 드롭다운 스타일(`FILTER_SEL_STYLE` 상수, `color:#1A2540` 명시)과 라벨 표기(콜론 없음, "PJT"→"현장명") 완전 통일.
- 10건 단위 페이지네이션 공통 적용.

### 프로젝트 상세 화면 레이아웃 개편
견적 내역/정산 내역을 세로로 쌓지 않고 **좌우 2단 배치**, 각각 고정높이(520px) + 내부스크롤 박스로 변경(`pdRenderEstList`/`pdRenderSetList`, `PD_PAGE_SIZE=10`). 항목이 아무리 많아도 페이지 전체 높이는 항상 일정.

### 견적/정산 상세 "뒤로가기" 진입 출처 추적
프로젝트 상세에서 견적/정산 항목을 눌러 들어가면 뒤로가기가 "프로젝트로 돌아가기"로, 견적/정산 목록에서 들어가면 기존처럼 "견적 목록"/"정산 목록"으로 분기(`estOrigin`/`setOrigin` 전역 변수, `openEst(id, fromPjtId)`/`openSettle(id, fromPjtId)` 두번째 인자로 출처 전달. `fromPjtId===undefined`면 기존 출처 유지 — 종결·수정 등 내부 새로고침 시 사용).

**⚠️ 배포 중 발견한 버그 2건 (교훈)**:
1. **템플릿 리터럴 보간 누락**: `onclick="openEst('${e.id}', id)"`처럼 변수를 `${}`로 안 감싸면, 실제 값이 아니라 **"id"라는 리터럴 문자열**이 그대로 HTML에 박힌다. 브라우저가 클릭 시 존재하지 않는 전역변수 `id`를 참조해 조용히 실패. → onclick 등 인라인 핸들러에 JS 변수를 넣을 땐 반드시 `${}`로 감싸고, 배포 후 실제 생성된 HTML의 속성값을 직접 확인해야 함.
2. **탭(화면) 전환 누락**: 이 앱은 `.view` 요소에 `on` 클래스를 토글해 화면을 전환하는데(`tabSilent(t)`), `pjtDetail()`은 `#v-pjt`의 **내용**만 새로 그리고 **화면을 그쪽으로 전환하는 처리**(`tabSilent('pjt')`)가 없었음. 같은 탭(pjt) 안에서만 호출될 땐 문제없었지만, 견적 탭에서 "프로젝트로 돌아가기"처럼 **다른 탭에서 크로스로 호출**되는 경우 내용은 바뀌어도 화면은 안 바뀌는 버그로 나타남. → 크로스탭으로 호출될 수 있는 렌더 함수는 항상 `tabSilent()`를 명시적으로 호출해야 함.

**검증 방식**: 텍스트/라벨 확인에 그치지 않고, 실제로 생성된 onclick 속성 문자열을 추출해 `vm.runInContext`로 그대로 실행하고, `class="on"` 토글 상태까지 추적해 "진짜 클릭했을 때 벌어지는 일"을 재현 검증함.
